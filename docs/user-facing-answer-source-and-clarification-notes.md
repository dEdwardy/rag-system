# 用户体验向能力备忘：回答来源标识与澄清式问答

更新时间：2026-04-05

## 背景

当前项目在 trace、diagnostics、report 等治理能力上已经相对完善，但普通用户通常不关心这些中间过程。

用户更直接关心的是：

- 能不能更快得到答案
- 答案准不准
- 这次回答是否可信
- 当前答案是来自内部资料，还是来自外部补充

因此，后续如果要继续增加能力，优先考虑用户可感知的体验增强，而不是仅服务管理员的治理能力。

## 目标

围绕当前 RAG 主链路，优先考虑两个用户向增强方向：

1. 回答来源标识
2. 澄清式问答

这两个方向都应保持低侵入，不重开新的 agent 平台，不引入明显超出当前产品边界的复杂交互。

## 方向一：回答来源标识

### 目的

让用户在答案区域一眼知道本次回答主要基于什么来源，从而降低误解，提升信任感。

### 推荐的最小来源分类

- `内部资料`
- `外部搜索`
- `混合来源`
- `通用补充`

### 面向用户的含义

- `内部资料`：本次回答主要依据当前知识库内容
- `外部搜索`：本次回答主要参考外部公开信息
- `混合来源`：本次回答结合了知识库内容和外部公开信息
- `通用补充`：当前未找到足够依据，下面是一个通用解释或补充说明

### 产品价值

- 用户可以更快判断是否应该信任当前答案
- 当未来接入外部搜索时，可避免用户误以为所有答案都来自内部知识库
- 当资料不足时，可以明确说明边界，而不是让用户误把模型补充当成正式依据

### 展示建议

- 优先做成回答区域的轻量 badge 或短标签
- 避免做成技术化字段或复杂诊断区块
- 重点是让用户一眼看懂，而不是展示内部系统细节

## 方向二：澄清式问答

### 目的

当用户问题模糊、歧义较大，或者第一轮检索结果质量较差时，不直接给出可能答偏的长答案，而是先帮助用户缩小问题范围，再回到 RAG 主链路。

### 推荐流程

```text
用户提问
-> 正常进入一次 RAG 检索
-> 若问题模糊或结果质量较差
-> 由 LLM 生成简短澄清问题或 2-3 个候选方向
-> 用户选择或补充
-> 再次进入 RAG
-> 输出正式答案
```

### 关键边界

- LLM 在这里主要负责“澄清问题”，而不是替代 RAG 直接回答事实性问题
- 最终正式回答仍优先由知识库检索结果支撑
- 如果资料仍不足，优先明确告知“当前资料不足以确认”，而不是默认让 LLM 自由发挥

### 适合的用户场景

- “报销怎么弄？”
- “权限怎么申请？”
- “合同怎么走？”
- “这个政策现在还能用吗？”

### 产品价值

- 降低答偏概率
- 降低用户重新组织问题的负担
- 提升用户对系统“理解我在问什么”的感知
- 保持产品仍然是知识库问答，而不是泛化聊天机器人

## 不建议优先做的方向

如果目标是提升普通用户体验，以下方向暂不建议作为近期优先项：

- 面向用户暴露复杂 agent 概念
- 通用多工具调用
- 多 agent 协作
- 重型 planner / executor 架构
- 主要服务管理员的 trace 解释、治理工作台扩展、复杂调优面板

这些能力可能有后台价值，但未必是当前用户最直接感知的价值点。

## 当前建议的判断顺序

如果后续要做用户体验增强，建议优先顺序为：

1. 回答来源标识
2. 澄清式问答
3. 证据不足时的保守回答
4. 回答后的自然下一步建议

## 一句话结论

后续如果继续增加能力，应优先投入“用户能直接感知到更好用”的增强：

- 让用户知道答案来自哪里
- 当问题不清楚时，先帮用户问清楚

这类能力比继续扩展管理员治理能力或引入重型 agent 框架，更符合当前产品阶段和用户价值。
