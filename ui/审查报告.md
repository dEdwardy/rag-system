# UI 审查报告

审查时间：2026-03-22

审查对象：`http://localhost:5173`

审查方式：
- 基于真实本地运行页面巡检
- 路由覆盖：`/`、`/documents`、`/documents/:id`、`/knowledge-base`、`/assistant`、`/traces`、`/traces/:id`
- API 与前端均可访问：`http://localhost:3000/health` 返回正常
- 巡检截图输出目录：`output/playwright/ui-review/`

## 1. 结论摘要

当前 UI 已经明显进入“收口阶段”，不是重做阶段。

整体判断：
- 视觉基调已经统一到同一套深色工作台语言，主壳层、页面 hero、面板、边框和 accent 关系基本成立。
- `Chat` 已经具备当前版本里最强的产品感，是全站最接近可交付状态的页面。
- `Documents / Knowledge Base / Assistant / Trace` 已经完成风格迁移，但仍有一批“体验层最后 20%”的问题，主要集中在：
  - 假交互控件过多
  - 部分页面信息密度和空间利用失衡
  - 页面之间的信息层级尚未完全统一
  - 少量文案与开发态痕迹仍暴露在用户界面

一句话判断：

`B 主题已经站住，但现在最需要做的是体验收尾，不是再继续扩视觉概念。`

## 2. 当前做得好的地方

### 2.1 壳层和主题统一已经基本成立

- 左侧导航、顶部栏、页面 hero、面板圆角、暗色表面层级已经形成统一语言。
- 深色基底加紫蓝 accent 的方向现在是稳定的，不再像半成品拼接。
- 页面切换后的品牌感和产品感是一致的，至少已经不像多个独立页面。

### 2.2 Chat 页是当前最成熟的工作台

- 主工作区、会话栏、引用栏三者关系清楚。
- 对话流本身可读性不错，用户/助手消息气泡区分明显。
- 引用区和 trace 入口已经形成可用的信息闭环。
- 页面一打开就能理解产品核心用途，这一点比其他页面强很多。

### 2.3 详情页比列表页更稳

- `Document Detail` 和 `Trace Detail` 的双栏结构是合理的。
- 左侧状态/元数据，右侧主内容，这种分工清楚，扫读成本低。
- Chunk、citation、score 等复杂信息至少已经有可承载骨架，不会完全失控。

## 3. 主要问题

以下按优先级排序。

### P0. 存在明显“假控件 / 假交互”，会直接损伤产品可信度

这个问题是当前最应该先处理的。

具体表现：
- 顶部的搜索按钮、通知按钮看起来像可用功能，但目前没有行为。
- 顶部的知识库下拉看起来像可切换，但当前更像静态展示。
- `Chat` 顶部的更多操作按钮没有实际作用。
- `Chat` 输入区的附件按钮看起来支持上传，但当前没有可用能力。
- 右侧 `会话 / 引用` 两个 tab 看起来像切换控件，但当前内容区并没有真正按 tab 切换，仍然是两个 section 直接堆叠。

影响：
- 这是比视觉不完美更严重的问题，因为它会误导用户预期。
- 用户一旦试两次发现控件“像能点但没反应”，会直接降低对整站完成度的判断。

建议：
- 对尚未实现的控件，优先改成纯展示而不是可点击样式。
- 如果必须保留按钮外观，就加明确的 disabled 态或 tooltip，避免形成错误预期。
- `Chat` 右栏如果暂时不做真实 tab，就不要渲染 tab 样式，改为两个明确 section。

### P1. `Knowledge Base` 页空间利用失衡，右侧指标列太长，主区偏空

这是当前最明显的布局失衡页面。

具体表现：
- 页面右侧 6 个指标卡纵向堆叠，拉得过长。
- 左侧主区内容不算少，但由于信息块高度偏短，页面中下部出现大面积空区。
- 视觉重心被右侧“长条计数栏”拉走，页面不像工作台，更像“左侧内容 + 右侧统计栈”。

影响：
- 首屏的结构感是有的，但往下立即出现内容断层。
- 用户会感觉这个页面“看上去完整，但信息不够撑得住布局”。

建议：
- 把右侧指标从竖向长列改为更紧凑的二维分布，至少减少纵向拖拽感。
- 将底部 `运行摘要` 上提或拆入主区首屏，让主区形成连续阅读路径。
- 若当前数据量不大，优先压缩 hero 和摘要块高度，不要让页面显得“上实下空”。

### P1. `Assistant` 页信息密度偏高，但分组层级还不够强

这个页面已经能用，但当前更像“深色表单”，还不够像“配置工作台”。

具体表现：
- `Answer Policy` 和 `检索配置` 区块字段非常多，但字段间层级差不够明显。
- 多个 `NativeSelect / NumberInput / Switch` 连续排布时，扫描节奏偏平。
- 右侧 `工作台状态 / 保存检查点` 做法是对的，但主区依然略显拥挤。
- 页面底部出现 `enableHybrid`、`enableRerank` 这种开发命名暴露，属于明显的产品化收尾未完成。

影响：
- 用户能看懂，但不够轻松。
- 当前页面更适合熟悉系统内部结构的人，不够适合第一次配置的人。

建议：
- 强化 section 内部的小标题、说明文、字段组间距，形成更明确的阅读层次。
- 将“常用配置”和“高级配置”进一步区分，不要让所有字段在同一视觉权重上。
- 去掉任何开发态字段名或内部实现提示，界面只保留用户语言。

### P1. `Trace List` 和 `Trace Detail` 的信息优先级还不够“产品化”

这两个页面已经比过去完整很多，但目前仍偏“诊断工具视角”，产品视角还差一点。

具体表现：
- `Trace List` 中，卡片重复度较高，最新 trace id 与状态 badge 比用户问题本身更抢眼。
- 用户问题内容的可扫描性不够强，列表更像 trace 审计卡片，而不是“对话诊断入口”。
- `Trace Detail` 里 `命中的 CHUNKS` 承载合理，但 `原始载荷` 仍然占据较高存在感。
- 对普通用户来说，`raw payload` 价值低，容易把页面拉回“开发工具”气质。

影响：
- 对研发是有帮助的，但页面会显得偏硬、偏技术。
- 当页面目标是“帮助定位回答依据”时，当前重心还不够聚焦。

建议：
- `Trace List` 优先突出用户问题、时间、结果状态，减少长 id 的存在感。
- `Trace Detail` 里把 `raw payload` 明确降级为折叠区或次级区域。
- 强化“问题 -> rewrite -> citation -> chunk”这条主线，让页面更像可解释链路，而不只是数据面板集合。

### P2. `Documents` 页目前过于保守，首屏工作台感弱于其他页面

具体表现：
- 页面的表格化收口比较克制，但首屏内容过于单薄。
- Hero 是成立的，但下面只有一个短表格，导致页面气势迅速掉下来。
- 表头、badge、操作按钮都够用，但视觉记忆点较弱。

影响：
- 从产品功能上能用，但和 `Chat`、`Assistant` 相比，页面显得偏“后台列表”。

建议：
- 在不新增复杂功能的前提下，加强列表页首屏的信息锚点。
- 可以增加更明确的文档状态汇总或更紧凑的批量态摘要，但不要回到卡片大拼盘。

### P2. 全站小字与弱对比文本偏多，长时间使用会累

具体表现：
- 侧边栏分组标题、次级说明、meta 文本普遍偏小偏灰。
- 若在高分屏或亮环境下使用，部分信息的第一眼可读性一般。

影响：
- 单页看问题不大，但全站持续使用会增加疲劳感。

建议：
- 对频繁阅读的 meta 信息适当抬高对比度。
- 不要所有次级信息都用同一档灰度，应该区分“辅助说明”和“实际有效信息”。

### P3. 首屏仍有低优先级稳定性问题

当前浏览器控制台存在一个资源错误：
- `favicon.ico` 404

影响：
- 不影响核心交互
- 但属于明显的开发态噪音，建议顺手补掉

## 4. 分页面简评

### Chat

结论：`当前最佳页面，可作为其余页面的收口参照。`

优点：
- 中央对话区占比合理
- 会话栏和引用栏都已经有产品工作台味道
- 主任务非常明确

问题：
- 右侧假 tab 是当前最明显的体验瑕疵
- 顶部和输入区还有若干假按钮
- 某些消息底部 trace id 直接裸露，信息表达仍稍偏技术内部

### Documents

结论：`功能可用，但表现偏保守。`

优点：
- 列表很干净
- 操作入口直接

问题：
- 首屏太空
- 列表信息量少时，页面显得撑不起来

### Document Detail

结论：`结构合理，已接近完成。`

优点：
- 左状态右内容的分区有效
- chunk 卡片阅读体验尚可

问题：
- 当前 chunk 卡片之间还可以再加强层次差
- 若内容较少，右区也会出现明显留白

### Knowledge Base

结论：`风格已经统一，但布局仍需一次明显收口。`

优点：
- hero、身份区、状态区都已经成型

问题：
- 右侧指标列过长
- 主区下半段利用率不足

### Assistant

结论：`已可交付，但需要一次产品化去技术味收尾。`

优点：
- 右侧保存面板方向正确
- 基本配置结构完整

问题：
- 字段过密
- 说明层级不够强
- 存在内部命名暴露

### Trace List / Trace Detail

结论：`诊断能力已经上来，但产品可读性还需提升。`

优点：
- 已经形成完整的 trace 浏览入口
- detail 页面结构比列表页更成熟

问题：
- 列表的信息优先级不够友好
- detail 页面“开发诊断感”仍略重

## 5. 建议的下一轮 UI 收口顺序

建议按下面顺序推进，不建议并行乱改：

1. 去掉或降级所有假交互控件
2. 修正 `Chat` 右栏 tab 语义不真实的问题
3. 重排 `Knowledge Base` 的主副栏内容比例与指标布局
4. 对 `Assistant` 做一次“字段层级 + 文案产品化”收口
5. 降低 `Trace` 页的 raw payload 存在感，提升问题与引用主线
6. 补 `favicon.ico` 和其他明显开发态噪音

## 6. 建议的验收标准

当满足以下条件时，可以认为这轮 UI 基本收尾：

- 页面上不再出现明显的假按钮、假下拉、假 tab
- `Chat / Knowledge Base / Assistant / Trace` 的信息层级和节奏明显统一
- `Knowledge Base` 和 `Documents` 不再出现“大面积空但右侧很长”的失衡感
- `Assistant` 页面不再暴露内部实现命名
- `Trace` 页面主线是“问题与证据”，不是“原始开发载荷”

## 7. 最终判断

当前 UI 的问题已经不是“风格没定”，而是“最后一轮产品化收口还没做完”。

如果只选一个最值得优先处理的方向：

`先清理假交互，再做 Chat/Knowledge Base/Assistant 的最后一轮层级收口。`
