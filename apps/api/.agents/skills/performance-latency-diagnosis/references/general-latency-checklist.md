# 通用延迟排查清单

## 适用场景

- API 响应慢
- 页面首屏或交互慢
- 后台任务耗时长
- 外部依赖调用慢
- 数据库读写慢
- 链路里有多个阶段，但不确定该先打哪里

## 通用排查顺序

### 1. 先明确目标指标

先确认到底要优化哪个：

- 首字节
- 总响应时间
- 页面可交互时间
- 后台任务完成时间
- 并发吞吐
- P50 / P95 / P99

如果目标不清楚，后面很容易优化错方向。

### 2. 先拆阶段，不要先猜原因

至少拆出：

- 总 wall-time
- 队列等待
- 本地计算
- 数据库读
- 数据库写
- 外部 API 调用
- 缓存
- 后处理

如果某一段显著高，再继续往那一段拆细。

### 3. 区分“系统内部执行慢”还是“往返慢”

很多问题不是内部执行慢，而是：

- 网络往返
- 代理或网关
- pooler
- region 太远
- 连接开销

所以要把：

- 内部执行时间
- 应用侧 wall-time

分开看。

### 4. 先看中位数，再看异常点

不要只拿单条最慢请求下结论。

先看：

- 一批相似请求的中位数
- 慢样本是否稳定重复
- 还是偶发抖动

### 5. 先做低风险优化

优先顺序建议：

1. 补观测
2. 修连接路径
3. 降实现层浪费
4. 改查询或索引
5. 再考虑改业务语义

## 常见误区

- 看到慢就直接改业务逻辑
- 没有区分 wall-time 和内部执行时间
- 只看单条 trace 就下结论
- 为了速度直接牺牲质量或正确性

## 一句话结论

先把慢点定位准确，再决定优化哪一层。  
不要在根因不清楚时，先动最贵、最有副作用的那一层。
